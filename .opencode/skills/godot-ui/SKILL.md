# Godot UI — как строить интерфейс

Скил-конструктор: применяется ДО первой строки кода экрана. Цель — чтобы «хороший UI»
был свойством репозитория, а не удачей модели. Источник правил — `refactoring-ui`
(переложен на Godot), база стиля — дизайн-язык проекта (`Docs/Design/visual-language.md`,
см. K1 в `ROADMAP.md`).

## Железные законы (не требуют обращения к доке)

1. **Иерархия — это и есть работа.** Сделать «выглядит продуманно» — в первую очередь
   сделать видимой важность, а не раскрасить. Стена равноценных элементов читается
   как шум при любых цветах.
2. **Усиливай приглушением.** Не получается выделить главное — ослабь конкурентов,
   а не кричи громче.
3. **Каждое значение — из системы.** Кегль, отступы, цвета, тени, радиусы, толщины рамок —
   из шкал дизайн-языка. Никаких подогнанных «на глаз» one-off значений.
4. **Начинай с избытка пустоты и убирай.** Пространство, добавляемое до «перестало быть
   плохо», всегда недодаётся.
5. **Отступ вокруг группы больше отступа внутри неё.** Одно это правило чинит большинство
   «почему непонятно».
6. **Размер — не единственный рычаг.** Два веса (400/500 и 600/700) и три цвета текста
   (основной / вторичный / третичный) несут почти всю иерархию. Ниже 400 для UI-текста не уходим.
7. **Никогда серый текст на цветном фоне.** Нужное ощущение — сниженный контраст, а не
   «серость»: подбирай оттенок в hue фона с правкой насыщенности/светлоты, а не белый с alpha.
8. **Одно primary-действие на экран**, пара secondary, несколько tertiary. Разрушительное
   действие не обязано быть самым громким.
9. **Семантику выбирай по смыслу, стилизуй по иерархии.** `h1` — решение структуры документа,
   а не кегля; заголовки секций обычно ведут себя как подписи и должны быть мелкими.
10. **Свет сверху.** Выпуклое = светлее верхняя кромка + маленькая резкая тень снизу;
    вдавленное = тень сверху, светлее нижняя кромка. Вся глубина следует отсюда.
11. **Мера текста для баблов** — по шкале K1; межстрочный растёт с длиной строки и падает
    с ростом кегля.
12. **Не полагайся на один цвет.** Цвет поддерживает сигнал, который дизайн несёт ещё
    чем-то (форма, текст, положение).

## Порядок сборки экрана (не переставлять)

Нарушение порядка = переукрашенный и недоструктурированный интерфейс.

1. **Сначала фича, не каркас.** Проектируем саму функциональность, потом навигацию,
   контейнер, логотип.
2. **Сначала в grayscale.** Заставь отступы, размер и контраст нести иерархию, пока цвета нет.
3. **Ранжируй.** Контент → primary / secondary / tertiary; действия → одно primary,
   пара secondary, несколько tertiary.
4. **Раскладывай по шкалам.** Отступы/размеры/типографика — из системы; групповые отступы
   подчиняются закону 5.
5. **Мера и ритм.** Длина строки и межстрочный — по закону 11.
6. **Только теперь цвет**, затем **глубина**, затем **финишные штрихи** — строго в этом порядке.
7. **Пустое состояние проектируй вместе с фичей**, не после. Скрывай поддерживающий UI
   (табы, фильтры), который без контента ничего не делает.
8. **Проверь визуально** — по пикселям, не по коду (см. раздел ниже).

**Шаги 1–3 должны оставить след.** Перед первой строкой разметки выпиши короткий
бриф-комментарий в файл: ранжирование (primary/secondary/tertiary, одно primary-действие)
и значения токенов для шагов 4–6. Это делает процесс проверяемым, а не «якобы ясно в голове».

## Godot-специфика

- **Theme — единственный источник стиля.** Общий стиль — через `Game/resources/theme/ui_theme.tres`
  и именованные вариации типов (`TitleLabel`, `BodyLabel`, `MonoLabel`, `PrimaryButton`,
  `GhostButton`, `BubblePanel`). Inline `theme_override_*` — запрещён (см. `CodeStyle.md`, раздел «UI и тема»).
  Исключение — одноразовый случай с комментарием «почему».
- **StyleBoxFlat/StyleBoxTexture — отдельными ресурсами**, чтобы правились в редакторе, а не только кодом.
- **Тема подключена** в `Game/project.godot` → `gui/theme/custom`, иначе не подхватится.
- **Раскладка — контейнерами**, не ручными offsets. `MarginContainer`/`VBoxContainer`/`HBoxContainer`
  вместо расстановки позиций вручную. Ломать `anchors_preset` «наугад» — антипаттерн.
- **9-slice** — для баблов и панелей с растяжимыми рамками.
- **Шрифты** — OFL/CC0 в `Game/assets/fonts/`, включены в тему. Дефолтный шрифт Godot — причина
  «дефолтного вида» номер один.
- **Тема близко к правилу «ноль хардкода»**: размеры, цвета, длительности — не литералы.
- **Состояния интерактива обязательны** для каждого `Button`: normal / hover / pressed / disabled / focus.
- **Focus-навигация** (клавиатура/геймпад) — обязательна для всех интерактивных элементов.
- **Минимальная проверка раскладки** — 1920×1080 и 1280×720.

## Визуальная верификация

Чтение исходников — не проверка дизайна. Когда сцена рендерится:

1. `project_run` (godot-ai).
2. Дойти до нужного экрана (симуляция ввода через `game_manage`).
3. `editor_screenshot` на **1920×1080** и **1280×720**.
4. Судить по пикселям: мера, контраст, групповые отступы, поведение раскладки.

Результат, выведенный только из кода, помечается как **unverified**.

## Scope-guard

- Меняем только то, о чём спросили. Остальные находки — сообщаем, не трогаем.
- Не вводим новые зависимости и не меняем подход к стилю в проекте без явного согласия.
- Скил читается как инструкция и **не правится** в процессе работы: устарел или неполон —
  скажи пользователю.

## Когда НЕ применять

- Задача без визуальной поверхности: чистая логика, автолоады, конвертеры, CSV.
- Готовая сцена, где нужна только механика без правки вида.
- Разовые дев-утилиты без UI-требований (там допустим любой вид).
- Если стиль уже задан и задача — воспроизвести его в новой сцене: сначала `ui-review`,
  потом этот скил как конструктор.
